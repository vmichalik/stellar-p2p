# Mutual recovery authorization

`resolve(orderId, buyerTokens)` is an on-chain agreement for a single exact allocation. The escrow contract only accepts it for a `Reserved` or `Paying` order and requires authorization from both the buyer and seller. There is no timeout-based unlock after payment is locked and no administrator override.

The buyer is the transaction source. Soroban treats that source account as authorized by the buyer's transaction-envelope signature, so the buyer does not need a second address credential. The seller must provide a protocol 29 `ADDRESS_V2` authorization entry. The adapter simulates the `resolve` call in recording mode, accepts only that seller entry and, when RPC includes it, a source-account entry for the buyer. It checks every entry against the same contract, method, order id and token allocation, with no extra sub-invocation. It asks the seller wallet to sign the authorization preimage. The returned signature is independently verified against the Soroban authorization hash and network passphrase. The buyer separately signs the final envelope, and the adapter checks that the transaction source and verified envelope signer are the buyer.

The source wallet bridge must expose `signAuthEntry(preimageXdr, account) -> base64Signature`, backed by Freighter API 6.0.1 `signAuthEntry(preimageXdr, { networkPassphrase, address })`. Freighter returns the signature bytes; it does not return a signed transaction or a serialized authorization entry. The adapter uses SDK 17.1's `authorizeEntry` to apply the signature and the chosen expiry ledger to the original simulation entry. Older credential variants fail closed.

Before either wallet prompt, the durable journal reserves an action key scoped to the order and allocation. Before submission, the final prepared envelope is checked against the invocation and the configured fee cap, its transaction hash is journaled, and the wallet source signature is verified. Unknown submissions remain blocked for reconciliation. Receipts require a confirmed transaction matching the resulting chain state, order and exact token split; they are not derived from the local proposal.

The [host](host/README.md) and [browser workbench](browser/index.html) collect these requests through an origin-checked capability API. They bind each signing request to the expected account. The host keeps the SQLite journal across restarts. A demo approval cannot replace either signature. This is an operator workbench; production account sessions and access control need a separate review.

The fixtures cover a seller address entry alone and that entry plus an explicit buyer source-account entry. The [disposable testnet rehearsal](../evidence/release/testnet-rehearsal-2026-10-25.json) also confirmed the half split with the reviewed contract and programmatic keys. It caught an SDK serialization bug: editing the decoded operations array did not change the envelope. The adapter now rebuilds the operation and checks the signed entries through XDR round-trips. Freighter UI behavior is still unvalidated.
